# Semantic diff of two documents, built (plan-15)

`crates/mzdraw/src/diff.rs`: `diff(a, b) -> Vec<Op>` matches atoms, bonds and objects by id and writes the patch with operations of the table of `schema` only, in a fixed order: remove bonds, atoms, objects (one `remove` each); add atoms, bonds, objects (in the pool order of `b`); set atoms (`atom.set`, `atom.data`, `atom.ann`), bonds (`bond.set`, with `rev` for swapped ends), objects (`obj.set`); `move`, grouped by equal displacement (an arrow whose end points move with it is one move; a different end point is an `obj.set` in the frame before the move). A new element, or `el` said again, is how an explicit hydrogen count is taken away (the only way the language has), and the label is then said again. A bond with another pair of atoms under the same id, and an object or atom whose id changes kind, are removed and added.

`hunks(a, ops) -> Vec<Hunk>` groups a patch into hunks (`ids`, `ops`) a person can accept one by one: one connected piece of `a` joined by the bonds the patch adds, or one object; an id used by several operations keeps them together; a `remove` or `move` that touches several pieces is split. Any subset of hunks applies in order, to a valid document (tested). It takes `a` as well as the ops (the plan said `hunks(ops)`): two atoms moved by the same displacement are one piece or two only the document says, and splitting one molecule in two hunks would let a person accept half of a move. A patch with `rotate`, `flip` or `ring` (which `diff` never writes), an add that names no id (its id comes from the counter) or an operation that names nothing is one hunk, never a panic (tested for each).

Door: the replay request field `diff` (`{"diff": {"a": DOC, "b": DOC}}`, a document is an `mzdraw/1` object or its JSON text), read in `Request::read` like every field and a row of the `request` table of `schema.rs` (sections `diff` and `hunk` describe the answer `{"ops": [...], "hunks": [{"ids": [...], "ops": [...]}]}`; `docs/mzdraw.md` is generated from that table). The request stands alone and is NOT answered as `draw-result/1`: any other field, `report`, `dry_run`, `expect` and `id` included, is the keyed error `error.draw2.diffAlone` (so there is no dry-run or batch `id` for a diff; its answer is a pure function of the two documents, and a bad document is refused before anything is computed, which is the validate mode). A bad shape is `error.draw2.request`, an unreadable document `error.draw2.document` or `error.draw2.documentNewer`. `Editor::diff_with(&doc)` gives the patch from the drawing in the editor (tested). CLI twin: `mzlab-cli mol draw` with that request. Exit codes: the native example `replay` exits 1 for every keyed error (stderr `{"error_key", "params"}`) and 0 on an answer; the golden `refused` cases of `tests/data/log/diff.json` hold each key stable on both sides (wasm == native). What `mzlab-cli` maps a keyed error to (mzLab's table has 2 for an invalid request) is mzLab's and is not tested here. No page change.

Tests: `crates/mzdraw/tests/ops.rs` (the random sessions of the undo property, in pairs: `apply(diff(a, b), a)` has the bytes of `b`, `diff(a, a)` is empty, the patch is in the fixed order, any subset of hunks applies, the SMILES of the result is `b`'s); `tests/data/log/diff.json` (section `diffs`, wasm == native by `tests/parity.mjs`; refused requests). Check: `tools/diff/run.py`, not an independent proof: the oracle is byte equality of `mzdraw/1` documents produced by our own diff and our own replay. RDKit (2026.09.2) adds a canonical-SMILES and InChIKey agreement on the pairs it can read (151 of 186 pairs, equal 151/151); both SMILES are written by `mzlab-mol`, so once the bytes are equal RDKit can only agree and would catch a bug of the SMILES writer only. The other 35 pairs (19%) are invalid in RDKit on both sides (an edit made a valence it refuses) and are compared by bytes alone. Reference output `tests/data/diff/reference.json` (seed 15, 200 structures, 186 pairs made, 14 not made because an edit or the import was refused): bytes equal 186/186, every hunk alone 186/186, all hunks in order give `b` 186/186. Edits covered: element, charge, isotope, radical, hydrogens, label, bond order, wedge, bond reversal, moves, atoms added and removed, objects added, moved, reshaped, removed. Not covered: rings, data and annotations, atom maps, arrow anchors. Exit codes: 0 pass, 1 a check failed, 2 tool error, 3 no RDKit.

Not built, said plainly:
- The counter `next` is not reproduced: no operation sets it, so the result of a patch has `next` at the highest id added (the tests compare with `next` of `b`). The order of a pool after a bond or an object is removed and added again is not `b`'s, and applying hunks in order puts the things of a later piece after those of an earlier one (the same drawing, a different pool order; the tests compare by id there).
- Unknown fields (`more` of the document, an atom, a bond or an object other than `data` and `ann`) are not compared: no operation writes them.
- An arrow anchor (`from`, `to`) that names an atom added by another hunk is accepted as written (a free end until that hunk is applied); an object is its own hunk.
- Matching by structure when ids differ (two drawings of different origin) and showing the diff (plan-16).
- A tiny displacement (under 0.00005) is no move; documents are kept to 4 decimals by the operations.
