# SDF out and the data of a structure, built

the data fields of an SDF record (`>  <name>`, the lines of its value, an empty line) are read, shown, edited and written. They live on the first atom of the structure, as the entry `data` of that atom in `mzdraw/1` (a list of `[name, value]` pairs in file order; a version that does not know the entry keeps it), so they follow the structure through undo, copy and every save of the document. One operation sets them, with its exact inverse: `{"op":"atom.data","id":1,"data":[["name","value"]]}` (an empty list takes them away); `Editor::set_data` is one undo step. What an SDF could not hold is refused with `error.draw2.data` and changes nothing: a name that is empty, longer than 80 characters, of more than one line or with `<` or `>`; a value with an empty line, a line that starts with `>` or `$$$$`, a control character, or more than 10,000 characters; more than 100 fields. Out, `save("sdf")`: one record per structure in document order (its molfile, its fields, `$$$$`), the same bytes for the same document; arrows and text are not in an SDF. In, a field header without a name in angle brackets and the fields beyond the limits are counted and said (`draw2.import.dataLeft`), never dropped silently. On the page: the button SDF under Save and the panel "Data of the structures" (a name and a value per field, Add a field, Apply; a field with an empty name is taken away). Not built: the data in the other formats (KET, CDXML and CML have places for properties), the title line of a record (written as `mzDraw`).
