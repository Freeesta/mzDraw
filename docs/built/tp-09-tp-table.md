# The TP table out (JSON, CSV) and the SDF round trip (tp-09), built

(`crates/mzdraw/src/tptable.rs` (the table and its two writers), `tp_list.rs` (a TP table is read back as a list; `table_order`, `ordered`), `editor.rs` (`save("tptable")`, `save("tptable-csv")`, `table_notes`, `lost_on_save`), `replay.rs` (the engine is attached for these outputs), `values.rs` (`Scan::measure_within`, caps of the caller), `io.rs` (`Imported::table_ignored`, `Imported::no_pathway`), `schema.rs` (two request rows), `crates/mzdraw-wasm/src/lib.rs` (`save_notes`), page `web/mzdraw.js`, `web/index.html`, `web/lang/mzdraw.js`; tests `crates/mzdraw/tests/tptable.rs` (23), `crates/mzdraw-wasm/tests/tptable.rs` (9, with the real engine); golden cases `tests/data/log/tp-table.json` (7); key table `docs/schemas/tptable-1.json`; independent check `tools/fidelity/tptable.py`, reference `tests/data/fidelity/tptable.json`; three e2e steps in `tests/e2e.mjs`.) No `draw_edit/1` op or field is new: the table is an output, the import of a table is the import of a list, so no property test of inverses is added. A log replays to the same bytes natively and in the `.wasm`.

A TP paper has a scheme and a table and the SI repeats both; kept apart, they disagree. Here the table is a view of the drawing: `{"out":"tptable"}` (`tptable/1`, JSON) and `{"out":"tptable-csv"}` give the rows of the pathway; the Save list of the page has the same two entries ("TP table (JSON)", "TP table (CSV)", the files `drawing.tptable.json` and `drawing.tptable.csv`), and the download is the bytes of `save(...)` and of the replay.

## The columns (stable; the key table is `docs/schemas/tptable-1.json`)

`tp_id, parent_id, generation, smiles, formula, monoisotopic_mass, adduct, mz_calc, mz_obs, ppm, rt, form_diff, mass_diff, level, identifier`.

| column | where it comes from |
|---|---|
| `tp_id`, `mz_obs`, `rt`, `adduct` | the reserved data `TP_ID`, `MZ`, `RT`, `ADDUCT` of the structure (tp-08, `tp_list::FIELDS`), as typed |
| `parent_id` | the `TP_ID` of the structure an anchored arrow leaves |
| `generation` | the layer of tp-05 (longest path from a root; 0 for a root); empty for a structure no anchored arrow touches |
| `smiles`, `formula` | the isomeric SMILES `save("smiles")` writes for that structure alone; the Hill formula of the record (no charge, no count 1) |
| `monoisotopic_mass`, `mz_calc` | the engine `sel` of mzLab through `values::Measurer` (arch-web-17): no mass is computed or typed in this repository; `mz_calc` is the mass plus the shift of the typed adduct, for the seven adducts of `display.adducts` |
| `ppm` | `(mz_obs - mz_calc) / mz_calc * 10^6`, from the typed `mz_obs` and the PRINTED `mz_calc` (so a reader recomputes it), 1 decimal |
| `form_diff` | the delta `TP - parent` of `pathway:label` (tp-07), spelling of `mzlab_mol::delta::print` (`+O`, `-CH2`, `+O-H2`); counted by the same code (`steplabel::Formulas`) |
| `mass_diff` | TP mass minus parent mass from the UNROUNDED masses, rounded once, signed (`+15.9949`, `-14.0157`) |
| `level`, `identifier` | the current entry of the annotation of the structure |

**Rows.** One row per structure and parent: a product with two parents (a convergent TP) has two rows, a root has one row with `parent_id`, `form_diff`, `mass_diff` empty. Rows are in the order `tp:number` numbers the products in (setting `pathway.number`: by layer then position, `mz`, `rt`), roots included; structures no anchored arrow touches come last, in the order of their first atom; a drawing with no anchored arrow has no pathway: the rows are in the order of the first atom and `generation` is empty. **Empty cells stay empty, never `0`**. An isomer has an empty `form_diff` and `mass_diff` `0.0000` (a number, not a missing value).

**Rounding, written once.** Masses, m/z and `mass_diff` have 4 decimals, `ppm` 1, all by the formatter of Rust (`{:.4}`, `{:.1}`): the exact decimal value of the binary number, ties to even (0.125 gives `0.12`, 0.375 gives `0.38`); `-0.0` is written `0.0`. `mass_diff` is rounded once from the unrounded masses, so it can differ by 0.0001 from the difference of the two printed masses (`-CH2` is `-14.0157`, the printed masses of the acid and its homologue differ by `14.0156`). `ppm` uses the printed `mz_calc`; against the unrounded m/z it would differ by up to 0.4 ppm. Half-to-even is Rust's, not a rule implemented here.

**NORMAN-style.** `form_diff` / `mass_diff` and the parent-TP pair rows follow what the NORMAN-SLE TP lists use (S66: `Form_Diff`, `Mass_Diff`, `ParentOrTP`; study §1 T4). The CSV is called NORMAN-style, never NORMAN-ready or compliant: no NORMAN validator was run, and the spelling is not S66's (see "The kill test" below).

## Notes: nothing is dropped in silence

Every cell left empty for a reason other than "the drawing has no such thing" is a keyed note (`Table::notes`): in the JSON (`notes`: key, count, the structures), in `lost` of a `draw-result/1` (`{"key","n"}`, the same mechanism as `draw2.export.mapsLost`), and on the page after the save (`#d2-ex-note` and the live line, in the words of `web/lang/mzdraw.js`; a test fails if a key has no text). Keys: `draw2.export.tpEngine` (no engine in this run: mass cells empty), `tpMass` (the engine refused the structure: an R group, an element with no valence rule such as `Na+`, more than 200 atoms), `tpAdduct` (an adduct that is not one of the seven: `[M+H-NH3]+`, `[M+2H]2+`), `tpCharged` (a charged structure has no adduct), `tpSmiles` (a structure above 500 atoms, or one the writer refuses), `tpParentName` (a parent with no `TP_ID`), `tpDelta` (a pair with no honest delta: a free-text label, or the same atoms with another charge), `tpNumber` (`mz_obs` or `rt` is not a number: copied as typed, with or without an adduct), `tpGuard` (CSV only, below).

Without the engine (the plain replay of `mzdraw`, the native route today) the mass cells are empty and `engine` is false; `mzlab-cli mol draw` must call `replay_with(request, n, Some(measure))` with the glue's `measure` as `values` already needs (arch-web-17, "For the CLI and mzLab"), until then the native route with masses is `cargo run -p mzdraw-wasm --example replay_glue`, which parity compares with the page.

**CSV** is RFC 4180: a field with a comma, a quote, a line break or a space at either end is quoted, `"` is doubled, lines end in LF. A text cell (`tp_id`, `parent_id`, `adduct`, `level`, `identifier`), and an `mz_obs` or `rt` that is not a number (an SDF field is any text), that starts with `=`, `+`, `-` or `@` gets a leading `'`, so a hostile field from an SDF is not a spreadsheet formula (counted as `tpGuard`; CSV only, the JSON is not changed). The importer takes that `'` off again (only a `'` before `=`, `+`, `-` or `@`, in a table header), so a guarded name round-trips; a name that merely starts with `'` is kept as written. The cells the module writes itself are not changed: **a spreadsheet may read `+O` or `-CH2` as a formula**, so import those columns as text.

## Reading a table back, and the SDF round trip

- **A table is a list.** `import` (the Add field, the file button, the request field `import`, `tp:import`'s `csv`) reads a CSV whose header has `tp_id` and `smiles` and only columns of the table as a TP list: `tp_id` is the name, `parent_id` the parent, `mz_obs` the m/z, `identifier` joins the level in the annotation (an identifier without a level is `tpRowLevel`). Rows with one `tp_id` are one product with several parents; two rows with one name and different cells are `tpRowDup` (a row failure of the atomic import). The 7 computed columns (`tp_list::DERIVED`) are **not read**: the page says so (`draw2.import.tpTableIgnored`) and the table calculates them again. A header that mixes the two kinds of column is `tpHeader`. The scale of an annotation is not in the table: a level that exists in both scales is read on the scale of Schymanski et al. 2014.
- **Round trip (tested, native and `.wasm`).** The CSV of tp-08 imported, `tptable-csv` exported, the export imported, `tptable-csv` exported again: the same CSV bytes, and the same document compared canonically (each structure's name, atoms, data, annotation and the centre of its atoms; each arrow's two names and text; no id).
- **SDF.** `out sdf` (built before) carries the reserved fields of tp-08 per record; reading it back gives the same data, annotations and table rows per structure (tested: formula, masses, m/z, ppm, `rt`, `level`, structure identity by `Mol::can`). **An SDF has no arrows**, so a re-read SDF has no pathway: `parent_id`, `generation`, `form_diff`, `mass_diff` are empty. It is listed, not dropped: `Imported::no_pathway` counts the records that carry `TP_ID` and the page says it (`draw2.import.tpNoPathway`). The CLI replay does not print the notes of an import (none of the formats does today); they are in `Imported::notes()` for the page.

## Limits, before any work

More than 15,000 atoms or 1,000 structures is `error.draw2.tpTableSize` (counted from the document and the scan, before the engine is called); the pathway layout refuses above 1000 anchored arrows (`error.draw2.schemeSize`) and a cycle (`error.draw2.schemeCycle`). The engine is asked once per structure (one run for the adducts the rows use). `to_smiles` keeps its 500-atom cap per structure (`tpSmiles`). The page's live structure check freezes with 6 or more identical molecules in a drawing (found by tp-03); the table does not run that check and does not change it.

**Cost** (native, `cargo test --release -p mzdraw --test tptable -- --nocapture`, stand-in engine, document built outside the timing, best of 5): 250 unlinked structures 13.6 ms, 1000 structures 54 ms; 100 linked 5.4 ms, 400 linked 21 ms (layout made before the timing). The two tests (`the_table_of_unlinked_structures_grows_linearly`, `..._of_a_pathway_grows_linearly`) bound the 4-fold size by 8 times plus a few ms. The mutation tried, `Document::part` per structure (a scan of the whole drawing for each one, which the first version had): 27.5 ms against 285 ms in release, 193 ms against 2245 ms in debug; the test fails in both. With the real engine and 1000 one-line rows the import and the table take 1.3 s in debug.

## The kill test (not run by the owner yet) and what the S66 header already says

The kill test asks the owner to paste the CSV into their SI table workflow once. That has not been done. What the run-time read of S66 shows already is a list of columns a NORMAN-SLE reader would need renamed or recomputed by hand, more than two, so they are a follow-up change of the column table before anyone builds a canvas table:
1. `form_diff` is `+O-H2` (the spelling of `mzlab_mol::delta`); S66 writes `H-2O1`, `C2H2O1`.
2. `formula` has no count 1 (`C10H14O`); S66 writes it for some rows (`C12H17N1O4S1`).
3. `mass_diff` has a plus sign on a positive value; S66 has none.
4. S66 has a row for the parent and one for the TP (`ParentOrTP`, `Eawag_ID_of_Pair`); here a row per parent-TP pair with `parent_id`.
5. Column names `SMILES`, `MolecularFormula`, `ExactMass`, `Form_Diff`, `Mass_Diff` are not the names here (the contract fixed ours).
6. `InChIKey` is not a column: there is no InChI in `mzlab-mol`. **Question for COO 16:** is an InChIKey from mzLab wanted (a new engine), or is the column left out for good? It is never faked. **Closed by the owner (21 Nov 2026): an InChIKey is NOT wanted now; do not build it.** The question to COO 16 is withdrawn.
