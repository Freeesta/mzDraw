# mzDraw: a molecule editor of our own (study and build plan)

mzDraw is a 2D structure editor written in Rust and compiled to wasm. It began inside mzLab (`Freeesta/mzlab`, where this study was written and where the files `drawing.md`, `drawing-menu.md`, the competitor matrix and the CLI route `mzlab-cli mol draw` live) and now stands in its own repository, `Freeesta/mzdraw`. The name lives in one place per layer: the crate names `mzdraw` / `mzdraw-wasm`, the constant `mzdraw::NAME` and the i18n key `draw2.name`.

Companion studies, copied from mzLab (written there, so their paths are mzLab paths): `mzdraw-competitors.md` (competitor matrix), `mzdraw-formats.md` (format conformity, settings, annotations; the built field list of annotations is `mzdraw-annotations.md`), `mzdraw-plan.md` (priorities and open decisions). Guidelines and standards (IUPAC, journal styles, format specifications, WCAG 2.2, colour) with a conformance checklist and the feature table: `study/arch-std.md`; its DEV prompts are `prompts/arch-std-NN-*.md`. Written here: `study/arch-web.md` (web and embeddable editors, the complete feature list with priorities and scriptable twins, the `<mzdraw-editor>` embedding API for the two hosts; DEV prompts in `prompts/arch-web-NN-slug.md`). Also written here: `study/arch-cd.md` (desktop editors: ChemDraw, BIOVIA Draw, MarvinSketch, ChemDoodle; the feature list with priorities and scriptable twins, palettes and context menus by target; DEV prompts in `prompts/arch-cd-NN-slug.md`, with the prompt to run where another study covers the same slice).

What to build next, in order and in waves, is one list: `docs/plan/backlog.md` (it merges the studies arch-std, arch-web and arch-cd, the external research input and the running work; new prompts `docs/prompts/plan-NN-*.md`).

## Built state (keep this section true in every PR)
- **Slice 1, built**: crate `crates/mzdraw` (document `mzdraw/1`, ids, atom/bond add/remove/move/set, ring templates, charge, exact undo/redo, command log, display list, hit-test, select/erase tools, SMILES/molfile/document in, molfile/SVG/document out), bridge `crates/mzdraw-wasm` with the live `check/1` of mzLab, page `web/` (published at the root of https://freeesta.github.io/mzDraw/), size cap `tools/wasm-cap.toml`, unit + property tests (`crates/mzdraw/tests/`), golden parity wasm == native (`tests/parity.mjs`), Playwright e2e of 8 steps with mouse, keyboard and touch (`tests/e2e.mjs`).
- **Slice 2a, built**: wedge marks on single bonds (`s` of a bond: solid, hashed, wavy; narrow end = atom `a`; tools `bond:up` / `bond:down` / `bond:wavy`, keys `W`, `Shift+W`, `Y`; a second click turns the wedge around). The marks are the drawing: the molfile carries them as drawn and the stereo of the record is derived by the molfile rules of `mzlab-mol`; a SMILES or molfile with stereo arrives with the wedges `mzlab-mol` writes for its record on our coordinates. Operations `rotate` and `flip` (commands on the selection or on everything; a flip keeps the marks, so it gives the other enantiomer). Clipboard: copy, cut, paste, duplicate (`Ctrl+C/X/V/D` and buttons); the system clipboard carries a molfile as plain text and the document under `application/x-mzdraw+json`. The log language gained `bond.add.s`, `bond.set` with optional `o`, `s`, `rev`, and the ops `rotate` and `flip`.
- **Positions of a structure without coordinates, built**: a structure that arrives without coordinates (a SMILES, a molfile without them) is placed by the 2D layout of `mzlab-mol` (`Mol::layout_2d`, D1, pinned at `ccd4680`; `layout::computed` turns its 1.5 Å bonds into the bond length of the drawing): rings as regular polygons fused along their shared bonds, chains as a 120° zigzag, every bond one bond length, pieces side by side (largest first). The import says that the positions were computed. A text with coordinates keeps them. The placeholder polygons of the earlier slices are gone. Not wired: "Clean up" of an existing drawing (`layout::clean_up` still returns the drawing unchanged).
- **Slice 2b, built**: atom labels (`lab` of an atom, `atom.set.lab` in the log; the empty text or a new element takes it away). An abbreviation of the table `crates/mzdraw/src/label.rs` (31 groups: Me, Et, Ph, Boc, NO2, CO2H, ...) is drawn as its name with lowered digits and expanded to its atoms in the record and the molfile (the expansion atoms follow the pool, with placeholder positions next to the label that can overlap the drawing). An R group (`R`, `R1` ... `R32`) is an `R#` atom with `M  RGP` in the molfile and the query atom `A` for the check; `mzlab-mol` refuses R groups, so a molfile with them cannot be imported yet and the `mol/1` record holds a helium stand-in. Label tool `label:<name>`, a field with the list in the toolbar, key `L`. The operations of the log are read by a hand-written reader (`Op::from_value`) instead of the derived one, which took 45 kB off the module (474,490 B; the cap stays 512,000 B, a raise is the owner's decision).
- **Slice 2c, built**: objects next to the molecules (`objects` of the document, ids from the same counter): reaction arrow (with an optional text above), plus sign, one-line text. Log ops `obj.add`, `obj.set`; `move` and `remove` take `objects`. Tools `arrow` (click = two bond lengths, drag = own length, levelled within 10 degrees; `Shift+A`), `plus`, `text:<line>` (a text field in the toolbar, key `T`; on an arrow it writes above it). Objects are hovered, selected, band-selected, dragged, erased, copied and pasted like atoms, and painted in the SVG. They are not in the molfile; rotate and flip leave them where they are.
- **Autosave, built**: the page writes the document to the browser's private file system (OPFS, file `mzdraw-autosave.json`) one second after the last change and when the tab is hidden. On the next visit a bar offers it (what it holds, Restore / Discard); what is worth offering is decided in Rust (`io::saved_summary`), and Restore opens the same bytes with an empty history (`Editor::open`). While the offer waits nothing is written. An empty canvas is not offered. Without OPFS there is no autosave and the page works as before. It is a page-only feature: the CLI reads and writes files.
- **Style and presets, built**: the settings file `mzdraw-settings/1` holds the drawing style in points (`crates/mzdraw/src/settings.rs`: bond length, line width, wedge width, hash spacing, double-bond spacing, label margin, font size, subscript scale, colour `element` or `mono`; every field optional, `preset` names the preset the others start from). Presets `mzlab` (default), `acs-1996`, `slides`; no RSC, Wiley or other journal preset until its numbers are read from the journal's guidelines. The style drives the screen and the SVG; the SVG is written in points, so it prints at the true size of the style. With this the default label size in files went from 14 to 12 (the file used 0.47 of the bond and the screen 0.4; one style now serves both and the screen kept its look), so SVG files saved before differ in size and label size from files saved now. It is not part of the document and is no undo step. The replay request takes `"style"` (a preset name or a settings object), so the CLI route gives the same bytes. Not built of the settings study: templates, abbreviations, shortcuts and editor sections (a file that has them keeps them, see below). The chosen style is remembered between visits: the page keeps the settings file the module writes (`style()`) in the browser (OPFS, `mzdraw-settings.json`) and gives it back to the module at the start; a file the module refuses is ignored.
- **Keyboard editing and the outline, built**: one atom has the keyboard focus (two rings on the canvas, `Overlay::focus`). Arrow keys walk along the bonds (the neighbour most in that direction), `Home` the first atom, `Page Down` / `Page Up` the next or previous structure, `Enter` / `Shift+Enter` grow a single or double bond (on an empty canvas `Enter` places a carbon), a letter sets the element of the focused atom, `1` `2` `3` the order of the bond just walked, `+` `-` the charge, `Space` selects the focused atom, `Delete` removes it, `Escape` leaves the focus. `Tab` is never taken: the study's "Tab = next piece" would trap the keyboard in the canvas (WCAG 2.1.2), so the pieces are on Page Down / Page Up. The page says where the focus is in the live line and shows "What is drawn": one line per structure with its Hill formula (`crates/mzdraw/src/outline.rs`, counted on the record, so abbreviations count as their atoms), tied to the canvas with `aria-describedby`. A closed help lists the keys. Not built: focus on a bond or an object, keyboard placing of arrows and texts, rebinding keys, a test with a real screen reader.
- **Drag-free editing (arch-std-05), built**: what a drag does is also possible with single actions or keys (WCAG 2.2 SC 2.5.7). With a selection and the canvas focused: `Alt+Arrow` moves it by 0.1 bond length, `Alt+Shift+Arrow` by 1, `Alt+[` / `Alt+]` turn it by 15° (about the mean of the atom positions, so 24 presses come back to the start within the 4 decimals of the document); each press is one `move` or `rotate` op in the log (no new operation), and presses of the same kind on the same selection within 1 s (time from the event stamp, no clock in Rust) are one undo step (`Session::run_into_last`). `Shift+Arrow` also adds the atom the focus walks to, and the bond between, to the selection. "Move here" (a `<button aria-pressed>` and key `M`, brings the select tool): a click or tap on an empty spot moves the selection so that its bounding-box centre lands there, one `move` op. The live line says each step (`draw2.announce.moved`, `draw2.announce.rotated`). The wasm `key` takes the event time stamp and Alt is bit 8 of `mods`. Not built: band selection by keys, focus on bonds and objects; on macOS `Option+[` types another character, so the turn keys work there only where the browser reports `[` / `]`.
- **Forward compatibility, built**: the version rule for both formats — this version reads `mzdraw/1` and `mzdraw-settings/1`; a higher number is the file of a newer mzDraw and is refused with a key of its own (`error.draw2.documentNewer`, `error.draw2.styleNewer`), never half read; a format change that an older reader could not survive bumps the number. Within a version, a settings file keeps the keys this version does not know (next to `format` and `style`, and inside `style`) and writes them back unchanged in alphabetical order (`Style::unknown`). The same holds for a **document**: fields this version does not know, on the document, an atom, a bond or an object (`More`, kept as JSON text), are kept by `Document::from_json`, stay on their thing through edits and undo, and are written back by `Document::to_json` after the known fields, by key. The document is now written by hand, as it is read. They are kept when a drawing is opened in place (`Editor::open`, the autosave restore); adding a file to a drawing, pasting and copying go through the operations, which carry the known fields only.
- **Touch and pen, built** (`crates/mzdraw/src/editor_touch.rs`; the page forwards every pointer with its id and time stamp and decides nothing): one finger uses the tool; two fingers pan and zoom the view around the point between them and never draw (the press of the first finger is dropped when the second lands, and a finger left over does not start to draw); a finger that lands within half a second of a pen event, or while the pen is down, is a palm and is ignored until it lifts, as is a third finger; a finger held still for half a second on an atom, a bond or an object selects it whatever the tool (the tool is kept); the eraser end of a pen (button 5) erases for one stroke and the tool comes back; a pointer the system takes away (`pointercancel`) commits nothing — before, it was treated as a release and could draw. The middle of a bond (30 % to 70 % of its length) now hits the bond even within reach of an atom: at the default zoom a finger reaches 22 px and half a bond is 20 px, so a bond could not be touched at all. Not built: pen pressure and tilt, a setting for "finger pans, pen draws", double-tap, measurements on a real tablet (the tests drive Chromium's touch emulation).
- **Still to build of slice 2**: flip that keeps the configuration (optional), import of abbreviations from files (R groups are read), free-text labels, multi-line and formatted text (sub/superscript runs), arrow kinds (equilibrium, retrosynthetic), RXN export, chains, forced-colours check, a pass with a real screen reader. **Slice 3**: molfile / SMILES / SDF, pictures that open again and KET are built (below); CDXML, RXN / RDF, CML / MRV are not.
- **Bounds**: ids stay below 2^31 and coordinates within 10^6 bond lengths and finite (`MAX_ID`, `MAX_COORD`): a document or an operation outside them is refused (`error.draw2.idTaken`, `error.draw2.coordinate`), so id arithmetic cannot overflow and no number that JSON cannot carry enters a document. Hostile input (deep nesting, huge arrays, long strings, extreme numbers) is refused without a panic, by test.
- **Slice 3a, built (formats: molfile and SMILES)**: out, `Editor::save` (one door for the page, the replay request `out` and the CLI): `molfile` (V2000; V3000 above 999 atoms or bonds), `molfile-v3000`, `smiles`, next to `mzdraw`, `svg`, `log`. The SMILES is the one `mzlab-mol` writes (Kekulé, stereo from the wedges as drawn, pieces joined by `.`) with the brackets a reader does not need taken away (`CC(=O)O`, not `[CH3][C](=[O])[OH]`); an R group is `[*]` / `[*:n]`. The V3000 file carries the wedges as `CFG` and the R groups as `R#` with `RGROUPS` (the V3000 text is the one of `mzlab-mol`, marked line by line). In: a molfile or an SDF, V2000 or V3000, every record side by side (64 at a time, the rest is said); SMILES, one or one per line with names; the R groups of all three forms come back as labels. Out of scope parts open and are listed in words under the Add field, never dropped in silence (`Imported::notes`): query atoms (read as unnumbered R groups), query bonds (read as single bonds), S-groups (left out), enhanced-stereo groups "and"/"or" (the centres keep their wedges, the grouping is not kept). A file whose coordinates do not fit a document is refused. Not read yet: the data fields of an SDF (`> <name>`), atom aliases, the atom lists themselves. Not written yet: SDF (one record per structure).
- **Slice 3b, built (pictures that open again)**: the SVG the editor saves carries its document (`mzdraw/1` as the text of a `metadata` element with the id `mzdraw`, `svg::carrying`; the picture itself is unchanged) and a new **PNG** does too (`png::finish`: an `iTXt` chunk with the keyword `mzdraw`, and `pHYs` so that the file prints at the size of its style). The pixels are made where a rasteriser is: the page draws the SVG of the module on a canvas of the size the module asks for (`png::plan`: 300 pixels per inch on white, fewer above 8192 pixels) and hands the bytes back. Opening either file (Open a file, or pasting the SVG) adds the drawing it carries, unknown fields included; a picture of another program is refused in words (`error.draw2.svgPlain`, `error.draw2.pngPlain`); the PNG reader checks every chunk length and the CRC of the document. The CLI route gets the SVG as before and can finish any PNG with `png::finish`; it has no rasteriser of its own.
- **Slice 3c, built (KET)**: the JSON format of Ketcher and Indigo, written and read from its published schema (`crates/mzdraw/src/ket.rs`, no code of theirs). Out (`save("ket")`): one molecule node with every atom (abbreviations expanded, R groups as `rg-label` atoms with `rg-n`, charge, isotope, radical, an explicit hydrogen count as `implicitHCount`), wedges as bond `stereo` 1 / 6 / 4 from the narrow end, arrows (`open-angle`), plus signs and texts as root nodes; the text of an arrow is a text node above its middle (KET has none on an arrow). In: every molecule of the file goes through the same door as a molfile, so aromatic bonds are kekulised and R groups, atom lists and other query atoms, query bonds and S-groups are treated and listed as there; arrows, plus signs and texts (rich-text content or a plain string; one document text per line) keep their place next to the atoms; shapes, images, multi-tailed arrows and R-group definitions are counted and said (`draw2.import.other`). Not read: `implicitHCount` (the valence rules decide), atom aliases, the stereo labels of enhanced stereo. The labels `D` and `T` are read as query atoms.
- **Slice 3d, built (CDXML)**: the XML form of ChemDraw files, written and read from the public CDX SDK documentation (`crates/mzdraw/src/cdxml.rs`; the pages read are the IUPAC copy of the SDK; no code of any other program), on a small XML reader of our own (`xml.rs`: element tree only, no DTD followed, no entity expanded beyond the five of XML and the numeric ones, depth and element count bounded). In: the nodes and bonds of every fragment (groups included) go through the same door as a molfile and a KET file; element nodes with charge, isotope and radical; a labelled node is an R group, an abbreviation of our table (the atoms of its inner fragment are not read: the label is kept) or, for any other label, element list or node type, a query atom; orders 1, 2, 3 and 1.5 (kekulised), any other order a query bond; solid and hashed wedges of both ends and wavy bonds; captions (style runs joined, one document text per line), `arrow` objects, line graphics with a head, plus symbols. Everything else (shapes, curves, brackets, orbitals, tables, spectra, embedded objects) is counted and said; colour and font tables and reaction schemes are passed over (they hold no content of their own). Out (`save("cdxml")`): one fragment in points, y down, 30 pt to the bond; hetero atoms with `Element`, `NumHydrogens` and a label; R groups as generic nicknames; wedges as `WedgeBegin` / `WedgedHashBegin` / `Wavy` from the narrow end; arrows as an `arrow` object plus the older line graphic that points at it, plus signs, texts. Not read: `NumHydrogens` (the valence rules decide), stereo attributes other than the wedges, bold and dashed displays, colours, fonts and text faces. Not confirmed on the pages read (marked in the module): the head of a line graphic is taken as the first point of its `BoundingBox`, and `ArrowheadHead="Full"` as a full head. Binary CDX is not read.
- **Slice 3e, built (reaction files)**: RXN V2000 and V3000 and RD files are read (`crates/mzdraw/src/rxn.rs`); RXN V2000 is written. A reaction file holds molecules and their roles, not a picture: read, the reactants are set on one line left of an arrow and the products right of it, with plus signs between them, and the agents (the third count of V2000, the `AGENT` block of V3000) above the arrow; every molecule goes through the same door as a molfile, so its R groups and out-of-scope parts are treated and listed the same way. The records of an RD file (`$RFMT` reactions, `$MFMT` molecules; 64 at a time, the rest is said) are set one under the other; their data (`$DTYPE` / `$DATUM`) is not read. Written (`save("rxn")`): the drawing must hold exactly one arrow (else `error.draw2.rxnArrow`, said under the Save buttons); a structure is a reactant, a product or an agent by where its middle stands along the arrow (before the tail, past the head, alongside), in order along the arrow, so a slanted arrow works; agents are written as a third count, an extension several programs read (without agents the counts line is the standard one). Plus signs, texts and the text of the arrow have no place in the file. Not built: atom-to-atom maps, RXN V3000 and RD files out, a drawing with several steps.
- **Slice 3f, built (CML and Marvin documents)**: one reader for CML (molecular convention) and MRV, the CML dialect of the Marvin documents (`crates/mzdraw/src/cml.rs`, on `xml.rs`; from the published convention, the MRV documentation and schema). In: every `molecule` with an `atomArray`, in the element form (`atom` children) or the array form (lists on `atomArray`), namespace prefixes or none; `elementType`, `x2` / `y2` (else `x3` / `y3`), `formalCharge`, `isotopeNumber` / `isotope`, `spinMultiplicity` / `radical`; the element `R` and `rgroupRef` are R groups, a dummy, a list or a pseudo atom is a query atom; orders `1 2 3`, `S D T`, `A` (kekulised), any other a query bond; `bondStereo` `W` / `H` from the first atom of its `atomRefs2` (else the bond's) and the MDL codes Marvin writes (1, 4, 6). Of a Marvin document also the reaction arrow, the reaction signs, the text boxes (their formatting in braces taken away) and the polylines with a head; its S-groups (nested molecules), R-group definitions and other graphics are counted and said. Names, formulas and properties of CML are passed over. Out (`save("cml")`): CML only, one `molecule` (abbreviations expanded, R groups as the element `R` with a label, wedges as `bondStereo`); CML has no place for arrows, plus signs and texts, so they are not written. Not read: `hydrogenCount` (the valence rules decide), `atomParity`, cis / trans `bondStereo` (the coordinates say it). Not stated in the pages read: the direction of y for `x2` / `y2`, taken upwards as in a molfile. MRV is not written.
- **Settings, one schema**: the numbers of the style are one table in Rust (`settings::FIELDS`: key, unit, bounds, accessors); the reader, the writer, the validation and the per-key setter `Style::set` all go through it, and `settings::schema_json()` gives it to any surface (`{"format", "presets", "colours", "fields": [{"key", "unit", "min", "max", "default"}]}`), so the CLI of mzLab can reuse it as it is. One setting is written `<section>.<key>=<value>` (`Editor::set("style.line_width=2")`, the shape of `--set`; the one section of this version is `style`: the fields, `colour`, `preset`); the replay request takes `"set": [...]`, applied after `"style"`, and gives the same bytes as the page. A value outside its bounds, a key that is none or a setting that is not of that shape is refused with its key (`error.draw2.styleValue`, `error.draw2.styleKey`, `error.draw2.set`) and changes nothing. On the page the fields under "Your own values" are built from the schema; "Save settings" downloads the file the module writes and "Open settings" gives a file to the module; the last style is kept in the browser. Not built: the templates, abbreviations, shortcuts and editor sections.
- **SDF out and the data of a structure, built**: the data fields of an SDF record (`>  <name>`, the lines of its value, an empty line) are read, shown, edited and written. They live on the first atom of the structure, as the entry `data` of that atom in `mzdraw/1` (a list of `[name, value]` pairs in file order; a version that does not know the entry keeps it), so they follow the structure through undo, copy and every save of the document. One operation sets them, with its exact inverse: `{"op":"atom.data","id":1,"data":[["name","value"]]}` (an empty list takes them away); `Editor::set_data` is one undo step. What an SDF could not hold is refused with `error.draw2.data` and changes nothing: a name that is empty, longer than 80 characters, of more than one line or with `<` or `>`; a value with an empty line, a line that starts with `>` or `$$$$`, a control character, or more than 10,000 characters; more than 100 fields. Out, `save("sdf")`: one record per structure in document order (its molfile, its fields, `$$$$`), the same bytes for the same document; arrows and text are not in an SDF. In, a field header without a name in angle brackets and the fields beyond the limits are counted and said (`draw2.import.dataLeft`), never dropped silently. On the page: the button SDF under Save and the panel "Data of the structures" (a name and a value per field, Add a field, Apply; a field with an empty name is taken away). Not built: the data in the other formats (KET, CDXML and CML have places for properties), the title line of a record (written as `mzDraw`).
- **Annotations, built**: a structure carries how sure its identification is and on what evidence (`crates/mzdraw/src/ann.rs`; the field list is `docs/mzdraw-annotations.md`). The annotation is a list of entries, a history whose last entry is current: `level` (a string, never a number: `"1"`, `"2a"`, `"2b"`, `"3"`, `"4"`, `"5"` of Schymanski 2014; any other word is kept as read), `scale`, `identifier`, `evidence` (`kind`, `ref`, `note`), `scores`, `source`, `by`, `note`; keys this version does not know are kept. It lives on one atom of the structure as the field `ann` of `mzdraw/1`, set by one operation with its exact inverse (`{"op":"atom.ann","id":1,"ann":[...]}`); `Editor::annotate` adds an entry in one undo step. Out: the document (and the pictures that carry it), `L2b` under the structure in the SVG and the PNG, four data fields of an SDF record (`MZLAB_LEVEL`, `MZLAB_IDENTIFIER`, `MZLAB_EVIDENCE`, `MZLAB_ANN`), read back from them. What is not an annotation is refused with `error.draw2.ann`. On the page: the panel "Annotation of the structures". Scales (arch-std-14): the panel offers a scale, `schymanski-2014` (default) or `charbonnet-2022` (PFAS: `1a` to `5b`), from the one table `ann::SCALES`; the level list follows the scale, the entry is written with that `scale`, and a level not of the chosen scale stays allowed and is shown "of the file" (`Editor::annotate` takes the scale; no new field of `draw_edit/1`; the level list for a scale, with "of the file", is `ann::level_list`, given to the page by `ann_levels`). The meaning of each level is an i18n text `draw2.ann.level.<scale>.<level>`, a short paraphrase (the Table 1 of Charbonnet 2022 is an image that was not read: the PFAS meanings are to be checked against it). Not built: scores and source on the page, level-aware depiction of levels 4 and 5, the caption line, annotations in KET, CDXML and CML.
- **Labels that do not crowd, built**: a bond stops short of what stands on its side of an element symbol, not only of the symbol: the charge at the upper right (`O−` and `H3N+` with a bond leaving to the right), the hydrogens with their count, the mass number (`Painter::clear` in `scene.rs`, on top of the label margin of the style; a bond never loses more than 45 % of its length at one end, and one that leaves downwards passes under a raised charge unshortened). Hydrogens written on the left stand before the mass number (`H3 13C`; they were drawn over it). Covered by `tests/crowding.rs`; one line of one golden SVG moved (a bond end in front of a charge). A second pass on a sheet of 28 synthetic structures (`tests/data/flaw_sheet.smi`: ring NH, charged ring atoms, halides, silicon, wedges to labels, radicals, acids) fixed the three flaws seen first: a bond keeps clear of a symbol of two letters (`Cl`, `Br`, `Si` are wider than the label margin allows for); with bonds on both sides of a symbol the hydrogens stand under it, or over it when the bonds leave downwards (the NH of a ring was written `NH` into its ring bond), a count at the lower right of the H and the charge at the upper right of the symbol as before; the wide end of a solid or hashed wedge stops half a wedge width earlier in front of a label. Three golden SVGs moved in the lines these rules touch. Not done here: the positions of the atoms themselves (the 2D layout is the one of `mzlab-mol`, D1), charges moved to another corner when the upper right is taken, abbreviation labels.
- **UI study (not built yet)**: `docs/mzdraw-ui.md` sets the action hierarchy (12 primary buttons, flyouts, side groups), the movable palettes with their default docks and presets, the `layout` and `export` objects planned for `mzdraw-settings/1` (Rust slice R1), the built and planned key and the log twin of every action, and the icon list for the icon set and the light/dark tokens to come.
- **Drawing checks `std/1`, stereo family, built** (`crates/mzdraw/src/conform.rs`; section "Drawing checks" below): `conform::report(&Document)` gives findings `{key, grade, atoms, bonds, objects}`; the JSON `{"format":"std/1","checks":[...]}` is written by hand, ordered by key then smallest id, ids ascending, empty lists left out. One door for every surface: `Editor::save("std")` = the replay request `"out":"std"` (the CLI twin; deterministic bytes, parity wasm == native in `tests/parity.mjs`); an unknown `out` is the keyed error `error.draw2.request`. The report is read-only and no undo step. The page has a closed panel "Drawing checks": the bridge hands over `state().std` (`{none, lines: [{key, grade, n}]}`, recomputed after each change; `none` is decided in Rust and the page only shows its text), a line selects what its findings are about (`select_check(key)`: the selection is view state, not a log operation, so it has no CLI twin). ## Architecture
```
mzlab-mol (record, readers, writers; later layout + SVG)      no mzLab dependency
   ^
mzdraw (document, scene, commands, undo, tools, hit-test,     depends on mzlab-mol, serde, serde_json only
        display list, settings, format registry)
   ^                          ^
mzdraw-wasm (wasm-bindgen)    mzlab-cli `mol draw` / mzlab-desktop
   + mzlab-feat[check]  = the thin mzLab glue: check/1, cip/1, i18n keys, OPFS autosave
```
- **Leaving the repo** = moving `crates/mzlab-mol` + `crates/mzdraw` (+ `mzdraw-wasm` without the `mzlab` cargo feature) and `mzlab/web/draw2/`. Guard: a test reads `cargo metadata` and fails if `mzdraw` gains a dependency outside `mzlab-mol`, `serde`, `serde_json`.
- **One wasm module** `mzdraw-wasm`, an entry of its own in `tools/moduli/` with its own cap. Targets: < 600,000 B raw, < 250,000 B gzip; the cap is the first measured size + 5 %. Owner lifted the limit on 2026-11-20; revisit before the first release (the cap is now a 4,000,000 B guard, see `tools/wasm-cap.toml`). Basis: `molkit` (record + readers + `check/1` + substructure) measures 352,069 B; the editor core is commands and geometry with no tables, estimated 80-120 KB on top of the readers.
- **Render path: Canvas2D for the live view, SVG from Rust for files.** Measured (scratch Playwright bench, Chromium, deviceScaleFactor 2, synthetic 500 atoms / 520 bonds / 150 labels, full repaint, median / p95): Canvas2D 2.4 / 3.2 ms; SVG DOM rebuild 3.6 / 7.5 ms script only, 814 nodes, plus style and layout before paint. With CPU throttled 4x (tablet class): Canvas2D 16.2 / 21.4 ms, SVG 17.7 / 28.9 ms script plus a frame at 27.5 ms.
  Canvas keeps a full repaint inside one 60 Hz frame on a desktop and close to it on a tablet with no DOM to keep in sync; a drag repaints only the display list, which Rust rebuilds in place. Hit-testing never needs DOM nodes (it is in Rust). To re-measure on WebKit on a Mac and on a real tablet in slice 2 (the cloud container has no WebKit build).
- **Display list**: Rust turns document + style + view state into a flat list of primitives (`line`, `poly`, `text`, `arc`, `rect`, each with a style index and the id of the object it paints), as one `Float32Array` plus a string table. JS paints it and nothing else; the same list serialised by Rust is the SVG, so the screen and the file cannot disagree. When the D2 SVG writer exists the list goes through it (one SVG writer in the workspace).
- **Input model**: JS forwards `pointerdown/move/up/cancel`, `wheel`, `keydown` as numbers (x, y in CSS px, pointer type, pressure, buttons, modifiers, key code); Rust owns the tool state machine, hit-testing (uniform grid over atoms and bond midpoints; radius 8 px mouse, 16 px pen, 22 px finger), snapping (30° steps, standard bond length), hover and the preview. Each event returns flags `{repaint, changed, cursor, announce}`. Target: event to display list < 1 ms for 500 atoms in wasm; pointer-to-paint within one frame.
- **Document model** `mzdraw/1` (below): objects with stable ids; a molecule object is a `mol/1` core plus what the record does not hold (2D coordinates as the user drew them, wedge marks as drawn, aromatic-circle display, abbreviation groups, R labels). Stereo follows the `mol.md` rule: the wedges are the drawing, the `stereo` elements are derived by the record's molfile rules at export, never the reverse.
- **Undo** = a command log in Rust. Every edit is a command with an exact inverse (the removed atoms and bonds are stored in the inverse); undo and redo are two stacks of commands, a drag is one command (coalesced). Property tested: any random command sequence then all its undos gives the identical document bytes, and redo gives the identical final bytes.
- **Command log = edit patch language.** The log is the JSON that `mol draw --set edit=` takes (D3). Until D3 is merged this is that language's draft: `[{"op":"atom.add","id":7,"el":"N","x":1.5,"y":0},{"op":"bond.add","id":9,"a":3,"b":7,"o":1},{"op":"atom.set","id":7,"chg":1},{"op":"move","atoms":[3,7],"dx":0.5,"dy":0},{"op":"remove","atoms":[7]},{"op":"ring","at":3,"n":6,"arom":true}]`. Ids are document ids, coordinates are in bond lengths (1.0 = one standard bond). D3 keeps or renames the ops; mzDraw follows, one language.
- **Determinism**: same document + same command log = same bytes from wasm, app and CLI (golden parity test). Floats are rounded to 4 decimals at the document boundary; no hash maps in serialised paths; no time, no randomness.
- **Accessibility**: the canvas is `role="application"` with a label; every tool is a real `<button>` with `aria-pressed`; full keyboard editing (a focus ring on one atom or bond, arrows move the focus along bonds, typing an element sets it, Enter/Shift+Enter grow a bond, digits set the order); every change is announced through an `aria-live="polite"` line built from i18n keys ("Atom N added, bonded to C3"); a text outline of the structure (formula, pieces, warnings) sits next to the canvas for screen readers; `prefers-reduced-motion` and forced-colours are honoured.
- **i18n**: Rust returns keys and parameters, never sentences; the page resolves them in `mzlab/web/lang/en/` (`draw2.*`). Tooltips are a name and a shortcut, nothing longer.

## Drawing checks (`std/1`)
A check never blocks and never changes the document. The list is `conform::CHECKS` (key, grade); the text of a key on the page is the i18n key `draw2.` + the key (`draw2.std.stereo.notCentre`). A possible stereocentre or stereo double bond is a site of `Mol::stereo_sites` of `mzlab-mol` on the record of the drawing (no second perception); sites on labelled atoms or on atoms that only the record has (an abbreviation's expansion) are left out. This is wider than the short atom list of the task text: it follows Table 8 of the InChI Technical Manual 1.07 as `mzlab-mol` encodes it (it also admits S and Se centres and strained N). Reading rules follow the Technical Manual: a wedge acts on its narrow end only; a wavy bond is an explicit "unknown". Thresholds are ours: 10 degrees.

| key | grade | what it flags |
|---|---|---|
| `std.stereo.wideEndCentre` | warn | solid or hashed wedge whose wide end is a possible stereocentre (the two InChI conventions read it differently) |
| `std.stereo.notCentre` | warn | wedge whose narrow end is not a possible stereocentre (not for the end of an allene) |
| `std.stereo.opposite` | warn | two solid or hashed marks at one centre on bonds within 10 degrees of 180 |
| `std.stereo.sameKindThree` | error | centre with three drawn neighbours and marks of one kind that do not fix the configuration: the Technical Manual construction (equal lengths, wide end of a solid wedge 45 degrees up, hashed 45 degrees down, implicit hydrogen on the other side) puts the centre outside the tetrahedron, which for same-kind marks means the centre is outside the triangle of its three neighbours |
| `std.stereo.collinear` | warn | two bonds of a centre within 10 degrees of one straight line, not both marked (two marks are `opposite`) |
| `std.stereo.wavyNotCentre` | info | wavy bond whose narrow end is no possible centre, and neither end is on a possible stereo double bond |
| `std.stereo.undefined` | info | possible centre with no mark at all (a wavy bond counts as a statement); possible stereo double bond with an end that has nothing drawn on it (a wavy bond counts as a statement; a double bond with substituents drawn is defined by its geometry) |
| `std.stereo.doubleCollinear` | warn | stereo double bond with a substituent within 10 degrees of its own line |
| `std.stereo.allene` | warn | allene (C with two double bonds and no other bond) with wedges at its ends that are not exactly two marks, one solid and one hashed, at one end |

Out of this slice: the five further stereo checks `fischerCross`, `reentrant`, `ringBond`, `hiddenH`, `relLabel` (follow-up prompt), the geometry checks (`std.geom.*`), export checks, CIP labels, automatic fixes. The older `check/1` of mzLab (valence, and a wedge from a non-stereocentre) stays as it is; the two lists overlap on that one case.

## Own document format `mzdraw/1` (open, versioned, round-trips everything the editor draws)
JSON, compact, fixed field order, the `mol/1` conventions (empty fields omitted, same document = same bytes):
`{format:"mzdraw/1", style:<name or object>, objects:[...], meta:{...}}`. Object kinds: `mol` (`id`, `atoms` and `bonds` as in `mol/1` with a stable `id` each, `xy`, `marks` = wedge/hash/wavy/aromatic display per bond, `groups` = abbreviations and their expansion, `rlabels`, `ann`), `arrow` (kind, points, text above/below), `text` (position, runs with sub/superscript), `plus`.
- `ann` on a molecule is the per-structure annotation: `{level: "2b", evidence: [...], scores: [{name, v, from}], source}`. The level is a STRING of the Schymanski 2014 set `"1"`, `"2a"`, `"2b"`, `"3"`, `"4"`, `"5"` (owner decision; it contains the plain 1-5), never an integer; a string outside the set is kept as read and written back unchanged. Details of the fields: `mzdraw-formats.md` §5. The slot and its rendering place (a badge and caption under the structure) are reserved from the first version; the identification features fill it later.
- A format change bumps the number; the reader of version N reads every earlier version (fixtures kept in `crates/mzdraw/tests/data/`). Unknown fields are kept and written back, so a newer file survives an older editor.
- Autosave: the page writes the document to OPFS (`mzdraw/autosave.json`, debounced 1 s after the last change, through the glue) and offers it on the next visit.

| PDF | no | yes | vector, text as text; no embedded fonts beyond the base 14 | later / small own writer on the display list |
| clipboard | yes | yes | writes `text/plain` molfile, `image/svg+xml`, `web chemical/x-mdl-molfile`, own `web application/x-mzdraw+json`; reads the same plus SMILES text, KET and CDXML text | 2 |
Every reader returns an import report (`{read, lost: [{what, count}]}`) shown after opening: the user sees what did not come through.

## Customisation: one settings file `mzdraw-settings/1`
One JSON file shared by the editor, the page and the CLI (`mol draw --set style=FILE|NAME`): `{format, style, templates, shortcuts, layout, export}`.
- `style`: bond length (pt), line width, bold width, hash spacing, double-bond gap, margin around labels, font family and size, subscript scale, atom colours (per element or all black), background, label placement (auto/left/right), explicit-H policy, terminal-carbon labels, aromatic rings as circles or alternating bonds.
- Built-in presets: `mzlab` (screen default), `journal-1996` (the ACS Document 1996 numbers: bond length 14.4 pt, line width 0.6 pt, bold width 2 pt, hash spacing 2.5 pt, double-bond gap 18 % of the bond length, Arial/Helvetica 10 pt, fixed length), `slides` (thick lines, large labels), `dark`. A preset is a settings file like any other; the numbers are public journal guidelines, no resource of another program is copied (`drawing-menu.md`).
- `templates`: named `mzdraw/1` fragments with an attachment atom or bond (rings 3-8, benzene, chair, common protecting groups); `shortcuts`: key to command.
- `layout` (the palettes: preset, snap distance, the palettes that differ from the preset) and `export` (`default` format of Save, `background` `white` or `none`): `docs/mzdraw-ui.md` §5. The file is validated by a JSON schema generated from the Rust types.

## CLI integration (`mzlab-cli mol draw`, with D1-D3)
- Whatever the editor produces, the CLI produces with the same Rust functions and the same bytes: `mol draw IN|- --set format=svg|png|pdf|molfile|ket|cdxml|mzdraw --set style=... --set edit=LOG`, `--json` with stable keys, exit codes per `cli-agenti.md`, data on stdout, progress on stderr, `--dry-run` = parse + check without output. Batch: several inputs or a stream on stdin (one SMILES or one JSON document per line, one result per line), no browser anywhere in the path.
- Replaying an editor session: `mol draw DOC --set edit=LOG` applies the same command log the editor recorded; the golden parity test compares its bytes with the wasm editor's.
- Speed gates (native, release, one thread, criterion-style bench in `crates/mzdraw/benches`, numbers written to this file when measured): command apply < 5 µs; document to display list < 50 µs and display list to SVG < 50 µs for a 30-atom molecule; layout + SVG for a small molecule in the tens of µs to low hundreds (the reference engines measure 10-180 µs median for layout alone, `agent-draw.md`); 500 atoms to display list < 1 ms.

## Interaction design: what the other editors teach
| editor | worth taking | to avoid |
|---|---|---|
| ChemDraw | hotkeys on the hovered atom (type `N` over an atom), click a bond to cycle its order, drag from an atom to sprout a bond at 30° steps with fixed length, journal presets, chemistry-aware labels typed as text (`OMe`, `CO2H`) | no resource or wording is copied; CDX fidelity is not claimed |
| Ketcher | open KET format, template library, floating right-click menu | iframe + worker + 12 MB Indigo; clipboard traps, a paste that rezooms, `localStorage` without guards (`drawing.md`) |
| Marvin JS | abbreviation groups that expand/contract, clear valence-error underline, good import dialog | server-side services for clean-up and naming |
| JSME | one-click simplicity and tiny size (a single small script), works on touch | no undo depth, no reactions with text, dated look |
| Kekule.js, ChemDoodle Web | object model with separate render and IO layers; ChemDoodle's lasso and hover feedback | size, licences (GPL for ChemDoodle Web) |
| OpenChemLib editor | fast, compact clean-up; stereo recognition while drawing | it reorders atoms and drops explicit H (`mol.md` trap) |
| PubChem Sketcher, MolView | import by name, immediate SMILES/InChI round trip in the page | server round trips for every edit |
Rules taken: (1) everything on the canvas is reachable in one gesture and reversible with one undo; (2) hover shows what a click will do (preview in a lighter stroke); (3) a wrong valence is marked while drawing, never blocked ("the user decides"); (4) no modal dialog for atom properties: a small popover next to the atom, usable from the keyboard; (5) a tap target is 40 px on touch; pen = precise tool, finger = tool or pan by setting, palm rejected while the pen is near (as `touch.js`). The full competitor matrix comes from the architecture study and replaces this table when it exists.

## Limits stated
- The page rasterises PNG from the SVG with a canvas; the CLI uses `resvg`: parity is on SVG bytes, not PNG bytes.
- The OPFS autosave and the system clipboard exist only in the page; the CLI reads and writes files and stdin/stdout.
- Text metrics: label widths come from a fixed table of advance widths for the preset fonts in Rust, so the layout is identical in wasm, app and CLI; a font outside the table falls back to the table of the nearest generic family.
